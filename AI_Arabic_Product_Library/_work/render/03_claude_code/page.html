عن هذا الدليل

هذا الدليل ليس شرحا لأوامر سطر أوامر. Claude Code أداة برمجة وكيلة تقرأ مشروعك وتعدل ملفاته وتشغل الأوامر، ولهذا فإن أهم ما ستتعلمه هنا ليس كيف تطلب منها، بل كيف تتحكم فيها: ما الذي تسمح به، وما الذي تراجعه، وكيف تتراجع عن تغيير، وكيف تبني ذاكرة للمشروع لا تعيد شرحه كل يوم. كل أمر في هذا الدليل مأخوذ من التوثيق الرسمي وقت المراجعة.

CHAPTER 01ما هو Claude Code ومتى تستخدمه

الوصف الرسمي في التوثيق: أداة برمجة وكيلة تقرأ الكود وتعدل الملفات وتشغل الأوامر وتتكامل مع أدوات التطوير، متاحة في الطرفية والمحرر وتطبيق الحاسوب والمتصفح. الكلمة المفتاحية هنا «وكيلة»: هي لا تقترح عليك كودا لتنسخه، بل تنفذ في مشروعك.

الواجهات المتاحة

التوثيق يذكر أن Claude Code يعمل على عدة واجهات، وكلها تتصل بالمحرك نفسه، فملفات CLAUDE.md والإعدادات وخوادم MCP تعمل عبرها جميعا:

  • الطرفية Terminal: الواجهة الكاملة، وهي التي يركز عليها هذا الدليل.
  • VS Code: إضافة تعرض الفروق داخل المحرر ومراجعة الخطة وسجل المحادثات.
  • JetBrains: إضافة لـ IntelliJ و PyCharm و WebStorm وغيرها، وتتطلب تثبيت الـ CLI منفصلا.
  • تطبيق الحاسوب: تطبيق مستقل لمراجعة الفروق بصريا وتشغيل عدة جلسات جنبا إلى جنب.
  • المتصفح: تشغيل المهام الطويلة بلا إعداد محلي على claude.ai/code.
ما الذي يتطلب اشتراكا

التوثيق يذكر أن معظم الواجهات تتطلب اشتراك Claude أو حساب Anthropic Console، وأن تطبيق الحاسوب يتطلب اشتراكا مدفوعا. كما تدعم واجهات الطرفية و VS Code و JetBrains مزودين خارجيين.

ما الذي يجيده فعلا

  • أتمتة العمل المؤجل: كتابة اختبارات لكود بلا اختبارات، وإصلاح أخطاء الفحص، وحل تعارضات الدمج، وتحديث الاعتماديات.
  • بناء ميزات وإصلاح أخطاء: يخطط، ثم يكتب عبر عدة ملفات، ثم يتحقق.
  • العمل مع Git مباشرة: تجهيز التغييرات وكتابة رسائل الـ commit وإنشاء الفروع وفتح طلبات الدمج.
  • الربط بأدواتك عبر MCP، والتخصيص بالمهارات والخطافات.

متى لا تستخدمه

لا تستخدمه على كود لا تفهمه ولا تنوي مراجعته. الأداة تنفذ، والمسؤولية عن مراجعة ما نفذ تبقى عليك. وهذه ليست نصيحة عامة: التوثيق نفسه يضع بندا اسمه مسؤولية المستخدم، ويقول إن Claude Code لا يملك إلا الصلاحيات التي تمنحها، وأنك مسؤول عن مراجعة الكود والأوامر المقترحة قبل الموافقة.

CHAPTER 02التثبيت والتحقق والتحديث

التوثيق يوصي بالمثبت الأصلي Native Install. المسارات التالية منقولة من صفحة التوثيق الرسمية وقت مراجعة هذا الدليل.

macOS و Linux و WSL

المثبت الأصلي — الطريقة الموصى بها
curl -fsSL https://claude.ai/install.sh | bash

Windows

PowerShell
irm https://claude.ai/install.ps1 | iex
موجه الأوامر CMD
curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd
أي صدفة أنت فيها

التوثيق يعطي علامة مميزة: إذا ظهرت رسالة أن && ليست فاصل جمل صحيحا فأنت في PowerShell لا في CMD. وإذا ظهر أن irm أمر غير معروف فأنت في CMD لا في PowerShell. موجه PowerShell يبدأ بـ PS C:\ بينما موجه CMD يبدأ بـ C:\ بلا PS.

Git for Windows على ويندوز الأصلي

التوثيق ينصح بتثبيت Git for Windows على ويندوز الأصلي حتى يستطيع Claude Code استخدام أداة Bash. وبدونه يستخدم PowerShell كأداة الصدفة. أما إعدادات WSL فلا تحتاج Git for Windows.

CHAPTER 03الجلسة الأولى: من فتح المشروع إلى أول تعديل

الخطأ الأول الذي يقع فيه معظم المستخدمين: يفتحون الأداة ويطلبون منها بناء ميزة فورا. الترتيب الصحيح: افهم، ثم خطط، ثم نفذ، ثم راجع.

الخطوات الخمس الأولى

  1. افتح المشروعمن داخل مجلد المشروع، شغل claude. لا تشغله من مجلد المنزل.
  2. افهم قبل أن تعدلاطلب شرحا للبنية قبل أي طلب تعديل.
  3. ادخل وضع التخطيطاستخدم Shift+Tab للتنقل بين الأوضاع، أو /plan، لتحصل على خطة قبل التعديل.
  4. راجع الخطةاقرأها فعلا. تعديل الخطة أرخص بكثير من تعديل الكود.
  5. نفذ ثم راجع الفروقبعد التنفيذ، شغل /diff لمراجعة ما تغير في شجرة العمل.

لماذا اسمان لوضع واحد

الوضع الذي يراجع كل إجراء اسمه Manual في الـ CLI وفي claude --help وفي إضافتي VS Code و JetBrains وفي تطبيق الحاسوب، لكن قيمته في الإعدادات هي default، وهي القيمة التي تستخدمها الخطافات وتكاملات الـ SDK. ويقبل الـ CLI الاسم manual كمرادف، مثل claude --permission-mode manual.

كيف تبدل الوضع

  • داخل الـ CLI: مفتاحا Shift+Tab.
  • في VS Code: مؤشر الوضع. وفي تطبيق الحاسوب: محدد الوضع.
  • عند التشغيل: claude --permission-mode plan مثلا.
  • من ملف إعدادات: المفتاح permissions.defaultMode.

في أي وضع تبدأ جلستك

التوثيق يوضح أن Claude Code يأخذ الوضع من أول ما ينطبق: العلم --permission-mode أو --dangerously-skip-permissions، ثم permissions.defaultMode في ملف إعدادات، ثم الافتراضي المدمج. وعلى خطط Pro و Max و Team في الطرفية أو عبر إضافة VS Code، الافتراضي المدمج هو وضع auto. أما مع claude -p أو الـ Agent SDK أو خطة Enterprise أو مفتاح Console فالافتراضي هو default.

قيمتان لا تعملان من ملفات إعدادات المشروع

التوثيق يذكر أن ضبط "auto" داخل .claude/settings.json أو .claude/settings.local.json لا يسري، وأن ضبط "bypassPermissions" في هذين الملفين لا يسري أيضا وتبدأ الجلسة في وضع Manual. بقية القيم تسري من أي ملف إعدادات.

ما لا يوافق عليه أي وضع تلقائيا

هذه القائمة من التوثيق مهمة لأنها تعني أن حتى أخطر وضع يبقى فيه سياج. لا يوافق Claude Code تلقائيا في أي وضع، بما في ذلك bypassPermissions، على:

  • الأدوات التي تطابق قاعدة سؤال صريحة.
  • الأدوات التي تتطلب تفاعل المستخدم مثل أداة AskUserQuestion.
  • عمليات rm و rmdir التي تستهدف مسارا حرجا — ولا توافق عليها قاعدة سماح ولا خطاف.
  • ضمانات المراسلة بين الجلسات.

ويذكر التوثيق أيضا أن قواعد المنع deny تمنع في كل وضع بما فيه bypassPermissions، بينما قواعد السماح allow لا أثر لها داخل bypassPermissions.

الوضع الخطر ومتى يجوز

قبل أن تفكر في تخطي الأذونات

الوضع bypassPermissions، ومعه العلم --dangerously-skip-permissions، ليس إعدادا افتراضيا ولا اختصارا للراحة. التوثيق يشترط لتشغيل مهمة غير مراقبة بهذا الوضع عزلا حقيقيا: حاوية أو جهاز افتراضي أو بيئة تشغيل معزولة، وعلى لينكس و macOS تشغيله بمستخدم غير الجذر.

لا تستخدمه على جهازك الشخصي وعلى مستودع فيه أسرار أو صلاحيات نشر.

بديل عملي أفضل من تخطي الأذونات

إذا كان دافعك كثرة الأسئلة، فالتوثيق يعرض مسارا أنظف: وضع Manual مع صندوق Bash الرملي في وضع السماح التلقائي. تشغله بـ claude --permission-mode default ثم /sandbox وتختار auto-allow. وتبقى قواعد المنع سارية، وتبقى قواعد السؤال التي تسمي أمرا بعينه — مثل Bash(git push *) — تسأل.

أمثلة إطلاق بأوضاع مختلفة
claude --permission-mode default
claude --permission-mode plan
claude -p "run the test suite" --permission-mode dontAsk \
  --allowedTools "Bash(npm test)" "Read"

CHAPTER 07مراجعة التغييرات والتراجع عن خطأ

هذا الفصل هو شبكة الأمان. أي شخص يستخدم أداة وكيلة سيمر بلحظة يعدل فيها الوكيل شيئا لم يكن يجب أن يعدل. المهم أن تعرف كيف ترجع.

  1. راجع الفرق أولاشغل /diff وانظر ما تغير فعلا، لا ما قيل لك إنه تغير.
  2. شغل الاختباراتقبل أي commit، لا بعده.
  3. اقرأ ما لا تفهمهإذا وجدت تغييرا لا تفهم سببه، اسأل عنه قبل الاعتماد.

نقاط الاستعادة Checkpointing

التوثيق يفرد صفحة مرجعية لـ Checkpointing، ويصفها بأنها إرجاع الكود والمحادثة إلى نقطة سابقة داخل الجلسة نفسها. وهي مختلفة عن التفريع: التفريع ينسخ المحادثة إلى مسار جديد، بينما الاستعادة ترجع بك إلى الوراء. كما تذكر صفحة الجلسات أن قائمة الاستعادة تحتوي مدخلا للجلسة السابقة يتيح الرجوع إلى ما قبل /clear داخل نفس عملية Claude Code.

أفضل حماية ليست ميزة داخل Claude Code بل عادة في Git. اجعل كل جلسة عمل تبدأ من حالة نظيفة معروفة:

قبل أن تبدأ جلسة تعديل

git checkout -b feature/my-task
claude
إذا ساءت الأمور

التوثيق يذكر حماية مهمة: في وضع Manual يستطيع Claude Code الكتابة فقط في المجلد الذي بدأ فيه ومجلداته الفرعية، ولا يستطيع تعديل ملفات في مجلدات أعلى دون إذن صريح. كما يسألك في وضع Manual قبل قراءة مسارات خارج هذا الحد بأدوات القراءة والبحث. ولهذا لا تشغل Claude Code من مجلد المنزل.

CHAPTER 08العمل مع Git والفروع وطلبات الدمج

Claude Code يعمل مع Git مباشرة: يجهز التغييرات، ويكتب رسائل الـ commit، وينشئ الفروع، ويفتح طلبات الدمج. الفائدة الحقيقية تظهر عندما تجعل ذلك جزءا من سير عمل منضبط لا أمرا عابرا.

سير عمل الفرع الواحد

  1. افتح فرعا لكل مهمةلا تعمل على الفرع الرئيسي مباشرة.
  2. اطلب خطة قبل التنفيذفي وضع التخطيط، لتراجع النطاق قبل أن يكتب سطر.
  3. نفذ ثم راجع/diff ثم الاختبارات ثم الاعتماد.
  4. commit صغير ومعنويرسالة تشرح لماذا لا ماذا.
  5. افتح طلب دمجواترك للمراجع فرصة حقيقية للفهم.

طلبات مفيدة مع Git

مراجعة قبل الاعتماد
راجع التغييرات الحالية في شجرة العمل قبل أن أعتمدها. أعطني: أولا. ملخص ما تغير، ملفا ملفا، في سطر لكل ملف ثانيا. أي تغيير لم أطلبه صراحة ثالثا. أي تغيير قد يكسر سلوكا قائما رابعا. ملفات كان يجب تعديلها ولم تعدل لا تعدل شيئا الآن. راجع فقط.
رسالة commit

CHAPTER 13الأمان: الأسرار ومراجعة الأوامر والمحتوى غير الموثوق

الحمايات المدمجة

  • نموذج قائم على الأذونات: في وضع Manual يبدأ Claude Code بصلاحيات قراءة فقط، ويسأل قبل تعديل ملف أو تشغيل أمر.

  • حد مجلد العمل: لا يكتب خارج المجلد الذي بدأ فيه ومجلداته الفرعية دون إذن.
  • صندوق Bash الرملي: عزل نظام الملفات والشبكة لأوامر Bash، يضبط بـ /sandbox.
  • تحقق الثقة: أول تشغيل على مستودع وأي خادم MCP جديد يتطلبان تحقق ثقة.
  • تخزين آمن للاعتمادات: المفاتيح والرموز تخزن في سلسلة مفاتيح macOS عند توفرها، وتحمى بصلاحيات الملفات على Windows و Linux.

حقن التعليمات أسلوب يحاول به مهاجم تجاوز تعليمات المساعد أو التلاعب بها عبر إدراج نص خبيث. التوثيق يذكر عدة حمايات، من أهمها عمليا:

المرحلة الثالثة: الأساس

  • أنشئ الهيكل والإعدادات وملف CLAUDE.md.
  • شغل /init ثم حسن الملف يدويا.
  • أضف الفحص والتنسيق والاختبارات من اليوم الأول.
  • معيار الانتقال: هيكل يعمل، واختبار واحد ناجح ولو تافها.

المرحلة الرابعة: الميزات الأساسية

  • ميزة واحدة لكل فرع ولكل جلسة.
  • خطة قبل التنفيذ، ثم /diff بعده، ثم الاختبارات، ثم commit.
  • معيار الانتقال: كل قصة مستخدم أساسية تعمل من طرف إلى طرف.

المرحلة الخامسة: الاختبارات

  • غط الحدود وحالات الفشل لا المسار السعيد فقط.
  • اجعل الاختبارات تعمل في التكامل المستمر لا على جهازك فقط.
  • معيار الانتقال: تستطيع تعديل الكود وأنت واثق أن الاختبار سيمسك الانحدار.

المرحلة السادسة: تجربة الاستخدام

  • رسائل الخطأ الظاهرة للمستخدم: مفهومة وتخبره ماذا يفعل.
  • الحالات الفارغة وحالات التحميل والفشل.
  • معيار الانتقال: شخص لم ير المشروع يستطيع إتمام المهمة الأساسية.

المرحلة السابعة: الأمان

  • لا أسرار في الكود، و.env مستبعد من Git.
  • تحقق من كل مدخل خارجي.
  • شغل /security-review على تغييرات الفرع.
  • معيار الانتقال: لا ثغرة حرجة مفتوحة.

المرحلة الثامنة: البناء

  • بناء نظيف من مستودع نظيف، لا من جهازك فقط.
  • وثق أوامر البناء في CLAUDE.md وفي README.
  • معيار الانتقال: يستطيع شخص آخر بناء المشروع باتباع التوثيق.

المرحلة التاسعة: مراجعة الإصدار

  • اختبر على بيئة قريبة من الإنتاج.
  • راجع سجل التغييرات وتأكد أنه يعكس ما تغير فعلا.
  • جهز خطة تراجع: كيف ترجع إذا فشل الإصدار.
  • معيار الانتقال: تعرف بالضبط ماذا ستفعل لو انكسر شيء بعد ساعة من النشر.
قاعدة المراحل

لا تنتقل لمرحلة قبل تحقق معيار انتقال السابقة. تخطي مرحلة لا يوفر وقتا، بل يؤجل اكتشاف المشكلة إلى مرحلة أغلى.

روتين الجلسة الآمنة

  1. git status — ابدأ من شجرة نظيفة.
  2. git checkout -b — فرع لكل مهمة.
  3. وضع التخطيط أولا، وراجع الخطة.
  4. نفذ، ثم /diff.
  5. شغل الاختبارات والفحص.
  6. commit صغير برسالة تشرح السبب.

أخطاء تجنبها

  • تشغيل Claude Code من مجلد المنزل بدل مجلد المشروع.
  • استخدام --dangerously-skip-permissions خارج بيئة معزولة.
  • اعتماد تغييرات بلا /diff وبلا اختبارات.
  • ملف CLAUDE.md ضخم بدل قواعد مرتبطة بمسارات.
  • جلسة واحدة طويلة لعدة أهداف مختلفة.
  • إضافة خادم MCP أو مهارة من مصدر لا تعرفه.
  • sudo npm install -g أو npm update -g لتحديث الأداة.

خطة الأسبوع الأول

  1. اليوم الأولثبت الأداة، وشغل claude doctor، وافتح مشروعا حقيقيا واطلب شرح بنيته.
  2. اليوم الثانيشغل /init وحسن ملف CLAUDE.md يدويا.
  3. اليوم الثالثنفذ تعديلا صغيرا في وضع التخطيط، وراجعه بـ /diff قبل الاعتماد.
  4. اليوم الرابعاضبط .gitignore و .env.example، وراجع /permissions.
  5. اليوم الخامساكتب أول قاعدة في .claude/rules مرتبطة بمسار.
  6. اليومان السادس والسابعنفذ ميزة كاملة بسير عمل المراحل، من الخطة إلى طلب الدمج.
